# Direct3D sharing

`vtkWin32OpenGLDXRenderWindow`, as the port's patches leave it ([VTK's patches](../netvtk-documentation/articles/design.md#vtks-patches), [Direct3D](../netvtk-documentation/articles/rendering.md#direct3d)).

- **The window could spare applications the 1 x 1 sharing** ([Direct3D](../netvtk-documentation/articles/rendering.md#direct3d)): NVIDIA's driver (RTX 2000 Ada, 616.92) keeps what a texture held when it was registered after being attached to a framebuffer, whatever the order it and the framebuffer are deleted in; a texture registered before it is ever attached costs nothing. The window would register a texture of its own and attach it in place of the render framebuffer's: a change to how it shares.
- **A re-created render framebuffer isn't shared again by itself.** Only the application's `SetMultiSamples` re-creates it now, and the application re-shares it (`RegisterSharedRenderFramebuffer`, after a render). For the window to do it: the re-creation happens in a render between `Lock` and `Unlock`, with the old texture locked; GL may give the new texture the old one's name, so the name doesn't tell; and each registration costs the texture's size with NVIDIA's driver (above).
- **Depth with reverse Z:** the shared depth texture is `D24_UNORM_S8_UINT` when the window has a stencil, which a reverse-Z window's float depth can't be blitted into; without a stencil it is `D32_FLOAT` and matches. Sharing colour alone (`RegisterSharedRenderFramebuffer`) is unaffected. `D32_FLOAT_S8X24_UINT` would take it, if the interop driver accepts that format.
